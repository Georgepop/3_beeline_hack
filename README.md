# Билайн Бизнес — диспетчерское планирование сервисных бригад

Веб-демо для хакатона ЛЦТ 2026. Приложение читает датасеты заявок регионов
(синтетические + контрольные распределения), строит план работ бригад
инженеров по смене и показывает его на карте с объяснениями.

## Возможности

- Заявки → план маршрутов бригад с учётом: навыков, типа транспорта,
  временных окон заказчиков, смены (08:00–20:00), нормативов времени работ и
  без возврата в офис.
- Три региональных датасета: `vostok`, `yugo_vostok`, `yugocentr`.
- Данные лежат в базе (SQLite по умолчанию, PostgreSQL — сменой `DATABASE_URL`),
  импортируются из CSV один раз: `python -m app.db import`. Переключать источник в
  рантайме не нужно — он один.
- **Правка данных прямо в интерфейсе**, изменения уходят в базу, а план
  пересчитывается сам: новая заявка по адресу или кликом по карте, правка и
  отмена существующих, правка смены/навыков/транспорта инженера, счётчик
  изменений и возврат к импорту по галочкам «заявки»/«инженеры».
- Солвер `improved` (срочные первыми + вставка по добавочному пробегу + 2-opt +
  вытеснение обычной заявки ради срочной); реестр позволяет добавить солвер
  коллеги/OR-Tools без правки фронта. Сравнение метрик — с базовым FIFO
  (считается на тех же данных) и с контрольным распределением (справочно).
- **Объяснения по каждой заявке**: клик по карточке заявки открывает, кто её взял,
  на какую позицию и почему, кто ещё мог взять и с каким добавленным пробегом, а для
  неназначенных — точную причину (код + человекочитаемая деталь) и что помогло бы
  её выполнить.
- **Сводка по плану** над картой: сколько заявок выполнено, предел смены по жёстким
  окнам, доля от возможного и ограничения, которые встали на пути.
- Сценарии перепланирования: внезапная срочная заявка, отмена заявки,
  недоступность инженера — с человеко-читаемым diff плана.
- Карта (MapLibre + растровые тайлы OpenStreetMap): маршруты бригад **по дорогам** (OSRM, с запасным
  вариантом «прямая линия»), стопы, офис, неназначенные заявки; переключатель
  «все маршруты / один инженер», чекбокс «Заявки на карте» с легендой статусов.
  План появляется мгновенно по прямым линиям, а дорожная геометрия догружается
  следом отдельным запросом и подменяет линии, не сдвигая вьюпорт.
- API по фиксированному контракту — солвер можно заменить, не трогая фронт.

## Стек

FastAPI + Pydantic, SQLAlchemy (SQLite по умолчанию, Postgres — одной переменной),
планировщик: свои эвристики (без тяжёлых зависимостей; OR-Tools — опциональный
бенчмарк). Геокодинг: Nominatim с кэшем и фолбэком на центры районов.
Карта/L-модель: MapLibre + растровые OSM-тайлы.

## Запуск

### Локально

```bash
py -3 -m venv .venv                  # Windows
.venv\Scripts\activate               # PowerShell
pip install -r requirements.txt
pip install -r requirements-benchmark.txt   # по желанию: режим-бенчмарк OR-Tools

$env:PYTHONUNBUFFERED = "1"
py -m app.db import                   # залить CSV в базу (мгновенно: data/parsed/ в репозитории)
uvicorn server:app --reload           # http://localhost:8000
```

При пустой базе импорт происходит сам при старте сервера — отдельно запускать
не нужно. Если нужно пересобрать данные из CSV (например, после правки файлов):
`py -m app.data_source build && py -m app.db import --force`.

`data/parsed/` лежит в репозитории: без него первый запуск ушёл бы в
геокодирование 205 адресов (~4–5 мин) и зависел бы от сети. Результаты
геокодирования кэшируются в `data/geocode_cache.json` (в игноре).

### Docker

```bash
docker compose up --build
# http://localhost:8000
```

Данные вынесены в volume `./data` — можно собрать кэш локально и передать его
в контейнер.

## Конфигурация (env / .env)

| Переменная | По умолчанию | Описание |
|---|---|---|

| `SOLVER_MODE` | `improved` | `baseline_fifo`, `improved`, `benchmark_ortools`, `ortools_office` |
| `DIST_MODE` | `haversine` | на расчёт не влияет, значение только отдаётся в ответе; дорожные метрики считает отдельный режим — см. `ORTOOLS_OFFICE_MATRIX` |
| `OSRM_ENABLED` | `true` | рисовать маршруты на карте по дорогам (OSRM); `false` — прямые линии. Для режима «Контур» этот флаг отключает ещё и матрицу расстояний |
| `OSRM_TIMEOUT` | `4` | таймаут запросов к OSRM (сек) |
| `OSRM_TABLE_MAX_POINTS` | `100` | сколько точек OSRM table берёт в одну матрицу |
| `SHIFT_START` / `SHIFT_END` | `08:00` / `20:00` | смена инженеров |
| `ORTOOLS_TIME_LIMIT` | `5` | лимит поиска, сек (потолок; 30 с давал +1 заявку на Юго-востоке) |
| `ORTOOLS_DROP_PENALTY` | `100000` | штраф за невыполненную заявку (мин) |
| `ORTOOLS_URGENT_PENALTY_FACTOR` | `3` | во столько раз выше штраф за срочную заявку |
| `ORTOOLS_FIXED_VEHICLE_COST` | `45` | плата за каждого задействованного инженера, мин |
| `ORTOOLS_FIRST_SOLUTION` | `parallel_cheapest_insertion` | стратегия первого решения |
| `ORTOOLS_LOCAL_SEARCH` | `guided_local_search` | локальный поиск |
| `ORTOOLS_OFFICE_MATRIX` | `osrm` | чем «Контур» считает длины дуг: `osrm` — дорожная матрица, `haversine` — по прямой |
| `ORTOOLS_OFFICE_WAIT_PENALTY` | `500` | штраф за простой инженера у окна в режиме «Контур»; `0` — выключить |

| GET  | `/api/requests` | `region` |
| GET  | `/api/engineers` | `region` |
| POST | `/api/plan` | `region`, `mode`, `dist` |
| GET  | `/api/plan/geometry` | `region`, `mode`, `dist` — только полилинии по дорогам |
| GET  | `/api/explain` | `region`, `request_id`, `mode`, `dist` |
| POST | `/api/scenario` | `region`; body: `{"type": "urgent"\|"cancel"\|"unavailable", "request_id"?, "engineer_id"?}` |

| GET  | `/api/health` | — |

### Правка данных

| Метод | Путь | Тело / параметры |
|---|---|---|
| POST   | `/api/requests` | `region`; body: `RequestDraft` (обязательны `address` и окно работ) |
| PATCH  | `/api/requests/{id}` | `region`; body: любые поля `RequestPatch`; `is_active: false` — отмена |
| DELETE | `/api/requests/{id}` | `region` |
| PATCH  | `/api/engineers/{id}` | `region`; body: `name`, `skills`, `transport`, `speed_kph`, `shift_start`, `shift_end` |
| GET    | `/api/db/status` | `region` — сколько добавлено/изменено/удалено против импорта |
| POST   | `/api/db/reset` | `region`; body: `{"requests": true, "engineers": true}` — обе галочки по умолчанию |
| POST   | `/api/geo/reverse` | body: `{"lat", "lng"}` — координаты клика → ближайший адрес |

Два способа создать заявку:

- **по адресу** — диспетчер вводит адрес; координаты подставляет сервер
  (геокодер с кэшем). Навык, норматив работ и срочность выводятся из типа
  заявки по справочникам, как при импорте.
- **по клику на карте** — координаты уже есть, адрес подставляет
  `/api/geo/reverse` (кэш в `data/reverse_cache.json`). Рядом с точкой может
  лежать соседний дом, поэтому адрес показывается редактируемым полем с
  предупреждением. Если геокодер не ответил, координаты всё равно сохраняются, а
  адрес вводится вручную.

Пересчёт плана после правки отдельным вызовом не нужен: кеш ключуется отпечатком
данных, и любая правка в БД сама его инвалидирует. Фронт после любой правки
перезапрашивает план и счётчик изменений, поэтому карточки, маршруты и метрики
всегда соответствуют базе.

Отмена заявки не удаляет её: в списке она попадает в отдельную группу
«Отменённые», остаётся на карте и возвращается в план снятием галочки
«Планировать в следующем рейсе». Для этого в контракте `Request` есть поле
`is_active`. Удаление — физическое, и отменить его можно только сбросом к
импорту; счётчик правок такие заявки тоже учитывает, поэтому кнопка сброса
не остаётся серой.

`/api/plan` возвращает `engineers[]` (маршруты: стопы с arrival/start_work/
finish/window), `unassigned[]` (с `reason`, `reason_code`, `reason_detail`),
`metrics`, `summary` (сводка) и `comparison` {baseline, improved, control}.
`GET /api/solvers` — список подключённых алгоритмов (реестр `app/solvers`).
Структуры — в `app/schemas.py`.

Почему расчёт не ждёт OSRM: в `/api/plan` у маршрутов всегда `route: null`, и
расписание считается целиком на haversine. Полилинии приходят отдельным запросом
`GET /api/plan/geometry` (`{region, mode, routes: [{engineer_id, route}]}`, где
`route` — `[[lat, lng], ...]` или `null`). Планировщик не делает сетевых вызовов
вообще: раньше это добавляло 12 запросов по одному на инженера и ~9 с к расчёту
региона. Отдельный endpoint отдаёт план из кэша и только догружает геометрию;
`data/osrm_cache.json` (в `.gitignore`) переживает перезапуск сервера, при
недоступности OSRM в `route` приходит `null`, и фронт рисует прямые линии.
Дорожные линии на карте и прямые — не выбор пользователя, а следствие того,
дошёл ли ответ OSRM: переключателя в интерфейсе нет намеренно.

Причины неназначения (`reason_code`):

| Код | Что означает |
|---|---|
| `no_coords` | нет координат — адрес не геокодирован |
| `no_skill` | нет инженера с нужным навыком |
| `no_transport` | требуемый транспорт отсутствует в регионе |
| `outside_shift` | работа не помещается в смену даже как единственная |
| `no_capacity` | подходящие исполнители заняты в свои окна |
| `solver_limit` | решатель не успел за лимит поиска |
| `model_mismatch` | маршрут решателя не прошёл проверку `core` |

## Хранилище

Единственный источник данных — база. Таблицы (`app/models.py`):

| Таблица | Содержимое |
|---|---|
| `regions` | офис, дата плана, метрики контрольного распределения, отметка импорта |
| `requests` | заявки + `is_active`, `origin`, `edited_at` |
| `engineers` | инженеры + `origin`, `edited_at` |
| `requests_baseline`, `engineers_baseline` | нетронутые снимки на момент импорта |

Baseline-копии — основа сброса к исходным данным: сброс это `DELETE` плюс
вставка из них, поэтому он всегда точен, даже если правили исходную строку.

Порядок поступления хранится в `ordinal`: идентификаторы строковые, и
сортировка по ним переставила бы заявки, а солверы к порядку чувствительны
(ТЗ — «заявки обрабатываются по порядку поступления»).

Перенос на PostgreSQL — сменой `DATABASE_URL` и установкой драйвера
(`pip install "psycopg[binary]"`). В коде только переносимые типы SQLAlchemy,
без `INSERT OR REPLACE` и прочего SQLite-специфичного.

### Что стало с данными коллеги

Раньше был переключатель «API коллеги». Он убран вместе с самим
интеграционным модулем: контрольный и синтетический CSV не имеют общих
идентификаторов заявок (ноль совпадений) и не совпадают по позициям, поэтому
статус и контрольную бригаду нельзя честно привязать к заявке. Привязка по
индексу повесила бы на заявку чужой статус. Статусы в таблице остались
(колонки `status`, `is_active`), но при импорте из CSV они пусты. Вопросы
коллеге — в истории проекта.

## Модель планирования (согласованные допущения)

- Бригада = 1 инженер; берётся как справочник из контрольного файла региона.
- Старт — офис региона; возврат в офис не планируется.
- Нормативы работ: Подключение 100′, Дозаказ 90′, Локальная 50′,
  Глобальная проблема/авария 40′; время дороги считается отдельно.
- Скорости (км/ч): авто 30, ОТ 20 (×1.5 на ожидание), вело 15, пешеход 5;
  для haversine — коэффициент кривизны дорог 1.3; тестовый прогон — пробег по дорогам.
- Навыки: `podklyuchenie` (Подключение/Дозаказ), `lokalnye`, `avariynye`
  (Глобальная проблема). Аварийные — приоритет `urgent`, выполняются первыми.
  Если срочная не помещается к занятому инженеру, `improved` делает одну попытку
  вытеснить из его маршрута обычную заявку и переселить её другому инженеру;
  в OR-Tools за пропуск срочной штраф выше в `ORTOOLS_URGENT_PENALTY_FACTOR` раз.
- Заявки «гигабит» требуют машину; заявки не начинаются раньше начала окна.
- Критерии (порядок): больше назначенных → меньше бригад → меньше пробега.
- Контрольное распределение — ориентир, а не обязательное совпадение.

## Бенчмарк: OR-Tools (`benchmark_ortools`)

Третий режим в селекторе алгоритмов — план на OR-Tools Routing (`app/solvers/ortools_solver.py`).
Ставится отдельно, чтобы демо работало и без него:

```bash
pip install -r requirements-benchmark.txt
```

Без пакета пункт в селекторе остаётся, но невыбираемым, а `/api/plan?mode=benchmark_ortools`
отдаёт 503 с подсказкой (раньше режим молча подменялся на `improved` — теперь нельзя).
То же относится к `ortools_office` — оба режима на одном пакете.

Модель: единый склад (офис), заявки — узлы с жёсткими окнами, каждая — опциональна
со штрафом `ORTOOLS_DROP_PENALTY`; инженеры — машины, совместимость по навыку и
транспорту через `VehicleVar`; возврата в офис нет. Целевая функция — **минуты**:
время в пути + плата `ORTOOLS_FIXED_VEHICLE_COST` за каждого реально задействованного
инженера, поэтому дуги инженеров на разном транспорте сравнимы между собой.
Планирование — те же нормативы, окна и скорости, что в `improved`, поэтому таймлайны
сопоставимы до минуты.

Замеры — `python -m app.bench` (свои данные, haversine, смена 08:00–20:00).
«Потолок» — сколько заявок в принципе назначаемо в смену при жёстких окнах:
есть координаты, есть подходящий инженер, работа целиком помещается в смену.

| Регион | Заявок | Потолок | FIFO | `improved` | `benchmark_ortools` | Пробег `improved` / OR-Tools |
|---|---|---|---|---|---|---|
| Восток | 66 | 58 | 39 | 57 | 57 | 212.3 / 166.2 км |
| Юго-восток | 83 | 77 | 39 | 62 | 59 | 582.1 / 399.9 км |
| Юго-центр | 56 | 48 | 28 | 48 | 46 | 170.7 / 126.3 км |

Замеры сняты при `ORTOOLS_TIME_LIMIT=5`. При 30 с на Юго-востоке выходило 60
заявок вместо 59 — см. разбор ниже про лимит поиска.

Выводы по замерам:

- `improved` закрывает потолок смены на 100 % (Восток 57/58, Юго-центр 48/48) и
  на 80 % на Юго-востоке (62/77). Разрыв с потолком — не качество алгоритма,
  а время в пути и медленный транспорт бригад.
- OR-Tools при том же покрытии тратит на 20–25 % меньше пробега и на 25–30 %
  меньше рабочего времени обедницы (например Юго-центр: 126.3 км и 5545 мин
  против 170.7 км и 7655 мин), но на Юго-центре оставляет 2 заявки, а на
  Юго-востоке — 3 меньше, чем `improved` (59 против 62). То есть на этих данных
  эталон проигрывает рабочему алгоритму по числу выполненных заявок, и это
  честный вывод, а не повод выкинуть режим: он нужен, чтобы было с чем сравнивать.
- FIFO отстаёт от `improved` на 18–20 заявок — это и есть требуемое ТЗ сравнение
  с базовым алгоритм; оно считается автоматически и показывается в интерфейсе
  (вкладка «Сравнение»): +18/+23/+20 заявок, при этом пробег на заявку падает
  с 5.3/12.0/5.3 до 3.7/9.4/3.6 км.
- Недостающие 1/15/0 заявок против потолка структурны: на Востоке и Юго-центре
  почти всё достижимо (57/58 и 48/48), на Юго-востоке разрыв в 15 заявок — это
  время в пути при медленном транспорте, а не качество алгоритма.

Лимит поиска — единственный измеренный рычаг качества OR-Tools, и он почти
не работает. Замерено на всех трёх регионах по 3 прогона: 5 с и 10 с дают
одинаковый результат (Восток 57, Юго-центр 46, Юго-восток 59), 30 с добавляет
**ровно одну заявку на Юго-востоке** — и появляется она между 25 и 30 секундой,
то есть это финальное улучшение GLS у самого дедлайна, а не устойчивый выигрыш;
60 с не даёт ничего сверх 30 с. Одна заявка из 83 не окупает 30 с ожидания,
поэтому потолок 5 с (`ORTOOLS_TIME_LIMIT`). Платить его приходится один раз на
версию данных: план лежит в `data/plan_cache.json` и переживает перезапуск.

Про стабильность: в ortools 9.15 у `RoutingSearchParameters` нет поля seed, и
результат зависит от того, сколько итераций успеет сделать машина за отведённое
wall-clock время. На повторных прогонах с одним и тем же лимитом разброс был 0,
но при смене загрузки машины наблюдался разброс в 1 заявку — поэтому цифры
`benchmark_ortools` ниже ориентир, а не гарантия.

Инструмент замера:

```bash
python -m app.bench                                   # 3 региона × 4 режима, медиана
python -m app.bench --region yugo_vostok --repeats 5
python -m app.bench --time-limit 60 --fixed-cost 20   # перебор настроек
python -m app.bench --transport-mix "auto=6,transit=3,bike=3" --engineers 3
python -m app.bench --mode ortools_office --office-matrix haversine   # «Контур» по прямой
```

Ничего не пишет в проект: переопределения настроек, нормативов, транспорта и
числа исполнителей применяются в памяти на время прогона.

Как устроен путь от заявки до маршрута, где проверяются ограничения и почему
`improved` выбран рабочим режимом — в [`docs/как-работает-решение.md`](docs/как-работает-решение.md).

## Режим «Контур» (`ortools_office`)

Четвёртый режим — независимая реализация на OR-Tools (`app/solvers/ortools_office.py`).
Код намеренно не делит ничего с `benchmark_ortools`: правка в общем модуле цепляла бы
режим, на котором зафиксированы цифры выше, а здесь своё всё, включая таймлайн.

Ключевое отличие — **инженер возвращается в офис, и это платится временем**.
Депо это узел 0, конец маршрута замыкается на него же, поэтому дуга
«последняя заявка → офис» занимает реальное время и должна уложиться в конец смены.
В `benchmark_ortools` и `improved` возврата нет. Остальные отличия:

| | `benchmark_ortools` | `ortools_office` («Контур») |
|---|---|---|
| возвращение в офис | не учитывается | оплачивается временем, упирается в конец смены |
| длины дуг | haversine × `ROAD_FACTOR` | дорожная матрица OSRM (направленная) |
| первая стратегия | `PARALLEL_CHEAPEST_INSERTION` | `PATH_CHEAPEST_ARC` |
| штраф за пропуск | 2 уровня: срочная ×3 | градация по типу заявки: Подключение ×5, Глобальная проблема ×1000, остальные ×1 |
| штраф за простой | нет | `SetCumulVarSoftUpperBound` на начало окна |
| таймлайн в ответе | `core.with_route`, haversine | собирается из решения OR-Tools, дорожные км |

Про штрафы: в OR-Tools `AddDisjunction(node, penalty)` — это цена **отказа** от узла,
поэтому вес 1000 у «Глобальной проблемы» означает максимальную защиту, а не запрет.
Направление совпадает с ТЗ 2.2 (срочность важнее), просто градация трёхступенчатая
вместо двухступенчатой.

Про длительности: в исходной реализации коллеги «Глобальная проблема» занимает
100 минут против наших 40 по ТЗ. Это норматив, а не алгоритм, поэтому режим
оставляет `duration_min` из импорта — иначе его метрики нельзя ставить рядом
с остальными режимами.

Матрица кэшируется в `data/osrm_cache.json` целиком, одним элементом на регион;
повторный план по той же версии данных сети не касается. При недоступности OSRM
режим не падает, а считает на haversine и честно пишет, чем считал, в
`PlanResponse.matrix`; `python -m app.bench` печатает то же в строке режима, иначе
невыполненный запрос выглядел бы как результат, посчитанный другой моделью.

Замеры, `ORTOOLS_TIME_LIMIT=5`:

| Регион | Заявок | Потолок | `improved` | «Контур» на OSRM | «Контур» на haversine |
|---|---|---|---|---|---|
| Восток | 66 | 58 | 57 / 212.3 км | 54 / 357.8 км | 57 / 330.3 км |
| Юго-восток | 83 | 77 | 62 / 582.1 км | 57 / 783.7 км | 61 / 809.3 км |
| Юго-центр | 56 | 48 | 48 / 170.7 км | 46 / 276.0 км | 46 / 235.8 км |

Читать надо с оговоркой, и она важнее самих цифр: **пробег «Контура» нельзя
сравнивать с пробегом остальных режимов напрямую.** На тех же маршрутах дорожная
матрица даёт в ~1.5 раза больше километров, чем haversine, и сверху платится
возвращение в офис — это заведомо больше работы, чем у остальных. Сопоставимы
только две вещи: число назначенных заявок и, с пересчётом на ту же модель дорог,
порядок обхода.

Вывод честный: на дорожной матрице «Контур» оставляет 2–5 заявок меньше
`improved` (54/57, 57/62, 46/48), и разрыв этот — цена возврата в офис и реальных
дорожных расстояний, а не просадка оптимизации. На матрице haversine тот же код
даёт 57/61/46, то есть вплотную к остальным. Режим оставлен не как «лучший», а
как способ увидеть, сколько стоит требование «инженер обязан вернуться в офис»
и дорожные расстояния вместо прямых.

Что проверено и что отклонено:

| Рычаг | Результат | Решение |
|---|---|---|
| Лимит поиска 10 → 30 с | +1 заявка на Юго-востоке, и только в последние 5 с | отклонено, потолок 5 с |
| Лимит поиска 60 с | +0 заявок | отклонено, лишние 30 с без пользы |
| Остановка поиска по застою | на 5 с потолка негде срабатывать, на 30 с убивала бы ту самую +1 заявку | не делали |
| `use_full_propagation` | 0 заявок на всех регионах | отклонено, настройки нет вовсе |
| Плата за инженера 45 → 20 / 0 мин | 60 / 62 при 10 с — шум ГС | оставлено 45, разница неустойчива |
| Транспорт: `auto=6` вместо 2 | +6 заявок (62 → 68) | не солвер, а входные данные: требует сверки с реальным парком |
| +3 исполнителя (все навыки, авто) | +11 заявок (62 → 73), но пробег 582 → 850 км | не солвер, а штат и расходы |

## Известные ограничения

- Пробег и время в пути считаются по haversine с коэффициентом кривизны дорог.
  `DIST_MODE` на расчёт не влияет: значение остаётся в контракте и отдаётся без
  использования. Дорожная геометрия для карты включается отдельно —
  `OSRM_ENABLED` (по умолчанию `true`).
- Исключение из предыдущего пункта — режим `ortools_office` («Контур»): он берёт
  у OSRM матрицу расстояний и считает расписание по ней, то есть **единственный
  режим, который при расчёте ходит в сеть**. Матрица кэшируется в
  `data/osrm_cache.json` целиком на регион, при недоступности OSRM режим считает
  на haversine и помечает ответ в `PlanResponse.matrix`. Побочный эффект: его
  пробег нельзя напрямую сравнивать с остальными режимами (дорога ≈ 1.5 × прямая).
- Принимается только агрегированный транспорт (тип инженера); гигабит-фильтр по огр.
- Организованное хранение исторических планов/настроек — таблицы `settings`,
  `plans` в SQLAlchemy (следующая итерация).
