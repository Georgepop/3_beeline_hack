### Правка данных

| Метод | Путь | Тело / параметры |
|---|---|---|
| POST   | `/api/requests` | `region`; body: `RequestDraft` (обязательны `address` и окно работ) |
| PATCH  | `/api/requests/{id}` | `region`; body: любые поля `RequestPatch`; `is_active: false` — отмена |
| DELETE | `/api/requests/{id}` | `region` |
| PATCH  | `/api/engineers/{id}` | `region`; body: `name`, `skills`, `transport`, `speed_kph`, `shift_start`, `shift_end` |
| GET    | `/api/db/status` | `region` — сколько добавлено/изменено/удалено против импорта |
| POST   | `/api/db/reset` | `region`; body: `{"requests": true, "engineers": true}` |
| POST   | `/api/geo/reverse` | body: `{"lat", "lng"}` — координаты клика → ближайший адрес |

Два способа создать заявку:

- **по адресу** — диспетчер вводит адрес, координаты подставляет сервер
  (геокодер с кэшем). Навык, норматив работ и срочность выводятся из типа
  заявки по справочникам, как при импорте.
- **по клику на карте** — координаты уже есть, адрес подставляет
  `/api/geo/reverse` (кэш в `data/reverse_cache.json`). Рядом с точкой может
  лежать соседний дом, поэтому адрес показывается редактируемым полем с
  предупреждением. Если геокодер не ответил, координаты всё равно сохраняются, а
  адрес вводится вручную.

Пересчёт плана после правки отдельным вызовом не нужен: кеш ключуется отпечатком
данных, и любая правка в БД сама его инвалидирует.

Отмена заявки не удаляет её: в списке она попадает в отдельную группу
«Отменённые», остаётся на карте и возвращается в план снятием галочки
«Планировать в следующем рейсе». Для этого в контракте `Request` есть поле
`is_active`. Удаление — физическое, и отменить его можно только сбросом к
импорту; счётчик правок такие заявки тоже учитывает, поэтому кнопка сброса не
остаётся серой.

`/api/plan` возвращает `engineers[]` (маршруты: стопы с arrival/start_work/
finish/window), `unassigned[]` (с `reason`, `reason_code`, `reason_detail`),
`metrics`, `summary` (сводка) и `comparison` {baseline, improved, control}.
Структуры — в `app/schemas.py`.

### Почему расчёт не ждёт OSRM

В `/api/plan` у маршрутов всегда `route: null`, и расписание считается целиком на
haversine. Полилинии приходят отдельным запросом `GET /api/plan/geometry`
(`{region, mode, routes: [{engineer_id, route}]}`, где `route` — `[[lat, lng], …]`
или `null`). Планировщик не делает сетевых вызовов вообще: раньше это добавляло
12 запросов по одному на инженера и ~9 с к расчёту региона. Отдельный endpoint
отдаёт план из кэша и только догружает геометрию; `data/osrm_cache.json` (в
`.gitignore`) переживает перезапуск сервера, при недоступности OSRM в `route`
приходит `null`, и фронт рисует прямые линии. Дорожные линии на карте и прямые —
не выбор пользователя, а следствие того, дошёл ли ответ OSRM.

### Причины неназначения (`reason_code`)

| Код | Что означает |
|---|---|
| `no_coords` | нет координат — адрес не геокодирован |
| `no_skill` | нет инженера с нужным навыком |
| `no_transport` | требуемый транспорт отсутствует в регионе |
| `outside_shift` | работа не помещается в смену даже как единственная |
| `no_capacity` | подходящие исполнители заняты в свои окна |
| `solver_limit` | решатель не успел за лимит поиска |
| `model_mismatch` | маршрут решателя не прошёл проверку `core` |

## Хранилище

Единственный источник данных — база. Таблицы (`app/models.py`):

| Таблица | Содержимое |
|---|---|
| `regions` | офис, дата плана, метрики контрольного распределения, отметка импорта |
| `requests` | заявки + `is_active`, `origin`, `edited_at` |
| `engineers` | инженеры + `origin`, `edited_at` |
| `requests_baseline`, `engineers_baseline` | нетронутые снимки на момент импорта |

Baseline-копии — основа сброса к исходным данным: сброс это `DELETE` плюс
вставка из них, поэтому он всегда точен, даже если правили исходную строку.

Порядок поступления хранится в `ordinal`: идентификаторы строковые, и
сортировка по ним переставила бы заявки, а солверы к порядку чувствительны (ТЗ —
«заявки обрабатываются по порядку поступления»).

Перенос на PostgreSQL — сменой `DATABASE_URL` и установкой драйвера
(`pip install "psycopg[binary]"`). В коде только переносимые типы SQLAlchemy, без
`INSERT OR REPLACE` и прочего SQLite-специфичного.

### Что стало с данными коллеги

Раньше был переключатель «API коллеги». Он убран вместе с самим интеграционным
модулем: контрольный и синтетический CSV не имеют общих идентификаторов заявок
(ноль совпадений) и не совпадают по позициям, поэтому статус и контрольную
бригаду нельзя честно привязать к заявке. Привязка по индексу повесила бы на
заявку чужой статус. Статусы в таблице остались (колонки `status`, `is_active`),
но при импорте из CSV они пусты.

## Модель планирования (согласованные допущения)

- Бригада = 1 инженер; берётся как справочник из контрольного файла региона.
- Старт — офис региона. В `improved` и `benchmark_ortools` возврат в офис не
  планируется; в режиме «Контур» возврата в офис нет — см. ниже.

  > В режиме «Контур» (`ortools_office`) инженер **возвращается в офис**, и это
  > платится временем: дуга «последняя заявка → офис» должна уложиться в конец
  > смены.
- Нормативы работ: Подключение 100′, Дозаказ 90′, Локальная 50′, Глобальная
  проблема/авария 40′; время дороги считается отдельно.
- Скорости (км/ч): авто 30, ОТ 20 (×1.5 на ожидание), вело 15, пешеход 5; для
  haversine — коэффициент кривизны дорог 1.3; тестовый прогон — пробег по дорогам.
- Навыки: `podklyuchenie` (Подключение/Дозаказ), `lokalnye`, `avariynye`
  (Глобальная проблема). Аварийные — приоритет `urgent`, выполняются первыми.
  Если срочная не помещается к занятому инженеру, `improved` делает одну попытку
  вытеснить из его маршрута обычную заявку и переселить её другому инженеру; в
  OR-Tools за пропуск срочной штраф выше в `ORTOOLS_URGENT_PENALTY_FACTOR` раз.
- Заявки «гигабит» требуют машину; заявки не начинаются раньше начала окна.
- Критерии (порядок): больше назначенных → меньше бригад → меньше пробега.
- Контрольное распределение — ориентир, а не обязательное совпадение.

## Структура проекта

```
app/
  config.py         настройки (env/.env)
  schemas.py        контракт API
  regions.py        справочники: навыки, нормативы, транспорт, регионы
  distance.py       haversine, время/время в пути, формат HH:MM
  geo.py            геокодер (Nominatim + кэш + фолбэк)
  data_source.py    парсер CSV → app/parsed/…json (используется только импортом)
  models.py         таблицы SQLAlchemy (рабочие + baseline-снимки)
  db.py             подключение, create_all, сессия на вызов, CLI импорта
  repository.py     единственная точка чтения/записи данных
  planner.py        диспетчер: данные + солвер + сравнение с FIFO + сценарии
  bench.py          замер планирования: 3 региона × 4 режима, потолок смены
  explain.py        объяснение по одной заявке (назначение и отказ)
  summary.py        сводка по плану: предел смены, доля, ограничения
  session.py        кэш последнего плана (объяснения считаются по факту плана)
  solvers/          реестр солверов; core.py (маршрут, потолок смены), fifo.py,
                    improved.py, reasons.py (причины), ortools_solver.py (бенчмарк),
                    ortools_office.py («Контур»)
  api.py            FastAPI-роуты
static/             фронт (index.html, app.js, style.css)
data/raw/<region>/  исходные датасеты; data/parsed/ — собранные модели
```
